**Structure the workflow with these steps:**

**`<purpose>`:** Initialize a project from spec files. Reads markdown specs from a folder, classifies each file's role, detects contradictions and gaps, synthesizes PROJECT.md. This is the spec-driven alternative to the interactive questioning flow in `new-project.md`.

**`<process>`:**

**Step 1: Setup and Initialization**
- Call `node ~/.claude/get-shit-done/bin/gsd-tools.cjs init new-project` to get context (reuse the existing init command — it provides `project_exists`, `has_git`, `is_brownfield`, `needs_codebase_map`, `commit_docs`, model configs, etc.)
- Parse JSON for needed fields
- If `project_exists` is true: Error — project already initialized, use `/gsd:progress`
- If `has_git` is false: `git init`
- Parse `$ARGUMENTS` to extract spec folder path (default: `./specs/`)
- Display initial banner:
```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 GSD ► READING SPECS

```

**Step 2: Existing `.planning/` Detection**
- If `.planning/` already exists with artifacts (PROJECT.md, ROADMAP.md, etc.), ask the user whether to overwrite:
  - Use AskUserQuestion with options: "Overwrite" (continue, will replace), "Abort" (exit)
- This satisfies CONTEXT.md decision: "If .planning/ already exists with artifacts, ask the user whether to overwrite"

**Step 3: Brownfield Offer**
- Same as new-project.md Step 2 — if `needs_codebase_map` is true, offer mapping
- Copy the exact pattern from new-project.md

**Step 4: Spec Folder Validation and File Reading**
- Validate spec folder exists: `ls "$SPEC_PATH"/*.md 2>/dev/null`
- **If folder doesn't exist:** Display actionable error:
  ```
  No spec folder found at ./specs/
  
  Create .md files there, or specify a path:
  /gsd:new-project-from-spec ./my-specs/
  ```
  Exit.
- **If folder exists but no .md files:** Display actionable error:
  ```
  No .md files found in ./specs/
  
  Add markdown spec files (.md) to this folder and try again.
  ```
  Exit.
- **If .md files found:**
  - Read all `.md` files from the folder (not recursively — top-level only)
  - Display progress: `Reading {N} spec files from {path}...`
  - For each file, read its full content
  - Display file list with sizes

**Step 5: Spec File Classification**
- For each spec file, classify its role by analyzing CONTENT (not filename):
  - PRD / Product Requirements
  - Technical Specification
  - User Stories / Use Cases
  - Architecture / System Design
  - Constraints / Non-functional Requirements
  - API Specification
  - Data Model / Schema
  - UI/UX Specification
  - Other / General

- Classification approach: The orchestrating agent (Claude) reads each file and assigns a role. No regex parsing — agent interprets content semantically.

- Display classification results:
  ```
  Classifying spec files...
  
  ✓ prd.md — Product Requirements
  ✓ tech-spec.md — Technical Specification
  ✓ user-stories.md — User Stories
  ✓ api.md — API Specification
  ```

- Store classification alongside file content for the synthesis step (Plan 02)

- Warn (don't error) about non-.md files in the folder:
  ```
  ⚠ Skipping non-markdown files: schema.json, notes.txt
  ```
