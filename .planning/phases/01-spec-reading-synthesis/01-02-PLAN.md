Analyzing {N} classified spec files...

The orchestrating agent (Claude) performs synthesis — this is NOT delegated to a subagent. The agent:

1. **Merges overlapping content:** When multiple specs cover the same topic (e.g., two files describe auth requirements), merge and keep the most specific/detailed version of each point.

2. **Detects contradictions:** Scan all classified specs for conflicts. Classify each as:
   - **Major contradiction:** Architectural or feature-level conflicts (e.g., "REST API" vs "GraphQL", "PostgreSQL" vs "MongoDB"). These require user input.
   - **Minor difference:** Wording/style differences, slight detail variations. Resolve automatically using the more specific version.

3. **Detects critical gaps:** Identify information that is critically missing — things that would significantly affect project structure if assumed wrong. Examples:
   - No target users defined
   - No tech stack preference stated
   - Core feature described but no success criteria
   - Conflicting priority signals

4. **Batches all questions:** Collect ALL contradictions and gaps found during analysis. Do NOT ask questions one at a time. Present them as a single batch after analysis completes.

5. **Cites sources in every question:** Each question MUST reference the specific file(s) and relevant quote(s):
   ```
   **Conflict 1: API Architecture**
   - `prd.md` says: "Build a REST API with standard endpoints" (line ~15)
   - `tech-spec.md` says: "Use GraphQL for all client-server communication" (section 3)
   → Which approach should we use? (REST / GraphQL / Hybrid)

   **Gap 1: Target Users**
   - No spec file defines the primary user persona or target audience
   → Who are the primary users of this system?
   ```

6. **Present questions using AskUserQuestion** (or markdown if many questions). Wait for responses.

7. **Classify extracted requirements** as per research SUMMARY.md:
   - CLEAR: Explicitly stated in specs, unambiguous
   - INFERABLE: Not stated explicitly but reasonably deduced from context
   - AMBIGUOUS: Could go either way, needs user input (should have been caught in conflict/gap detection above)
   Document INFERABLE assumptions in the Key Decisions table.

Display: `Asking about {N} conflicts and gaps...` (if any) or `No conflicts detected — specs are consistent ✓`

- This is non-intrusive and doesn't clutter the document

- Content from specs that doesn't map cleanly to PROJECT.md sections (detailed API schemas, data models, comprehensive user stories, etc.) is preserved as separate reference files

**Key Decisions import (from CONTEXT.md):**
